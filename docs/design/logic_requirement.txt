================================================================================
CBCMGROUPS EMAIL DISTRIBUTION LIST MIGRATION TOOL
Mailkeeper → MS365 Migration Requirements
================================================================================

PROJECT OVERVIEW
----------------
Migrate email addresses with specific domains (gmail.com, hotmail.com, etc.) 
from Mailkeeper distribution lists to MS365, allowing gradual retirement of 
the private email service while maintaining delivery reliability.

ARCHITECTURE
------------
- Python 3.10+ application with PyQt5 GUI
- MS Graph API for MS365 operations
- JSON-based migration state tracking
- Automatic backup and rollback support
- Standalone Windows installer for easy deployment

STEP 1: Setup Project Structure (parallel with step 2)

STEP 2: Create Mailkeeper Parser Module (parallel with step 1)
---------------------------------------------------------------
Parse .org file format:
- Check for MAILINGLIST directive to identify distribution lists (skip files without it)
- Extract ONLY plain email addresses (lines without ! prefix)
- Skip lines starting with ! (!ALIAS, !ACCEPT are commented out/inactive)
- Skip directive lines (MAILINGLIST, DELAYGREYLIST, NOTSENDER, etc.)
- Skip commented lines starting with #

Categorize emails by domain to match target domain(s)

Parse email metadata for MS365 contacts:
- Split email into username and domain
- First name: Remove all periods from username
- Last name: Remove all periods from domain, strip TLD (.com/.org/.gov/.net)
- Display name: {first_name} {last_name}
- Description: External contact - {original_domain}

Handle edge cases (malformed emails, special characters)

STEP 4: Build MS Graph API Integration Module (depends on 1)
-------------------------------------------------------------
- OAuth device code flow for authentication (user-friendly, no pre-registration needed)
- Create mail contact API call (for external emails with first_name, last_name, display_name, description)
- Create distribution group API call with owner assignment
- Add members to group API call (supports both mail contacts and internal users)
- Check if mail contact already exists (by email address) - return contact ID if exists
- Check if distribution group already exists (by email address) - return group ID if exists
- Check if member already in group before adding (avoid duplicate member errors)
- Validate owner email exists in MS365 organization
- Error handling and retry logic
- Rate limiting compliance

STEP 4.5: MS365 Credential Configuration (depends on 4)
-------------------------------------------------------
Secure credential file loading for MS Graph API authentication.

Credential Requirements:
- Azure AD Tenant ID (Directory ID): Unique identifier for Azure AD tenant (GUID format)
- Azure AD Application ID (Client ID): Identifier of registered Azure AD app (GUID format)
- MS365 Domain: Organization domain name (e.g., cbcmgroups.org)

credential.json Structure:
{
  "credentials": {
    "tenant_id": "12345678-1234-1234-1234-123456789012",
    "client_id": "87654321-4321-4321-4321-210987654321",
    "ms365_domain": "cbcmgroups.org"
  }
}

Key Features:
- User imports credential.json via UI button - no hardcoded credentials in code
- Credentials loaded into memory at runtime, never persisted to disk by application
- Credential values masked in UI display (show only first 8 chars + *)
- GUID format validation for tenant_id and client_id
- Domain format validation for ms365_domain
- Clear error messages for missing or invalid credentials

Implementation Files:
- src/utils/credential_loader.py: Load and validate credential.json
- credential.json.example: Template file for users with field descriptions
- .gitignore: Include credential*.json to prevent accidental commits

Security Best Practices:
- Never commit credential files to version control
- Restrict file permissions (Windows: NTFS permissions; Linux/Mac: chmod 600)
- Store in secure location, not on shared network drives
- Each user maintains their own credential file
- All authentication attempts logged for audit trail

STEP 5: Build Phase 2 - MS365 Export UI (depends on 3, 4)
----------------------------------------------------------
UI Components:
- "Load JSON" button to import migration file
- **Credential Management Section:**
  - "Import MS365 Credentials" button (file browser for credential.json)
  - Display credential status (Tenant ID*, Client ID*, MS365 Domain, Status indicator)
  - "Clear Credentials" button (remove from memory)
- Display summary and list preview
- Owner email input field: "Distribution List Owner" (required, validated as valid email)
- "Authenticate with MS365" button (OAuth flow, requires credentials loaded)
- "Create MS365 Distribution Lists" button (disabled until owner email provided, credentials loaded, and authenticated)
- Progress bar showing creation status
- Results log: success/failure/skipped for each contact and list (color-coded)

For each distribution list:
- Check if distribution group already exists in MS365:
  - If exists: Skip creation, log "Group already exists", mark as SUCCESS
  - If not exists: Create new group
- For each external email:
  - Check if mail contact exists in MS365
  - If exists: Skip creation, log "Contact already exists", mark as SUCCESS (already in MS365)
  - If not exists: Create new mail contact, mark as SUCCESS or ERROR
- Add all members to group (skip if already member)
- Track status for each email: SUCCESS, ALREADY_EXISTS, or ERROR

Phase 2 Outputs:
1. Verification JSON: Contains ONLY emails with status SUCCESS or ALREADY_EXISTS (safe to clean from Mailkeeper)
2. CSV log: Detailed report with columns: Distribution List, Email, Status, Action, Error Message (if any)

KEY DECISIONS
================================================================================

Technology:
- Python 3.10+ with PyQt5 (cross-platform, good library ecosystem)
- PyInstaller for creating standalone executable
- Inno Setup for Windows installer

MS365 Authentication:
- OAuth device code flow (user-friendly, works without pre-configured secrets)

MS365 Naming Convention:
- Append .ms365 before domain (e.g., badminton.ms365@cbcmgroups.org)

Comment Format:
- Migrated emails are prefixed with !ALIAS to comment them out (consistent with 
  Mailkeeper convention)
- The MS365 distribution list is added as an ACTIVE member (without ! prefix) to 
  enable email routing

Backup Strategy:
- Timestamp-based folders, keep indefinitely (user can manually clean)

JSON as State File:
- Human-readable, version-controllable, easy to edit if needed

Scope:
- Only process files with MAILINGLIST directive (skip personal aliases)

Email Extraction:
- Extract ONLY plain email addresses (no prefix)
- Lines starting with ! (!ALIAS, !ACCEPT) are commented out/inactive and should be skipped

Duplicate Contact Handling:
- Before creating mail contacts in MS365, check if they already exist
- If exists, skip creation and reuse existing contact
- This allows safe re-runs and sharing contacts across distribution lists

Email Parsing for MS365 Contacts:
- First name: Remove all periods from email username (e.g., hank.wang → hankwang)
- Last name: Remove all periods from domain part, strip TLD (e.g., hotmail.com → hotmail, fda.hhs.gov → fdahhsgov)
- Display name: {first_name} {last_name} (e.g., "hankwang hotmail")
- Description: External contact - {original_domain} (e.g., "External contact - hotmail.com")

Distribution List Ownership:
- Global owner approach - user specifies one owner email in Phase 2 UI that applies 
  to all distribution lists created in that session
- Owner email is validated to exist in MS365 before creation

Idempotent Operations:
- Tool checks if distribution groups and contacts already exist in MS365 before creation
- If they exist, skip creation and log as "already exists" with SUCCESS status
- This allows safe re-runs across different domains

Verification JSON Workflow:
Phase 2 exports two outputs:
1. Verification JSON: Contains ONLY emails with SUCCESS or ALREADY_EXISTS status (safe to clean from Mailkeeper)
2. CSV log: Detailed status report for all emails (Distribution List, Email, Status, Action, Error Message)

Safe Cleanup:
- Phase 3 uses verification JSON (not original migration JSON) to ensure only 
  successfully migrated emails are commented out (prefixed with !ALIAS) in Mailkeeper
- The MS365 distribution list is added as an ACTIVE member to route emails
- Emails with errors remain active for retry

Deployment Strategy:
- Create standalone Windows installer using PyInstaller + Inno Setup
- Bundle all dependencies so MS365 admins can install without Python
- Include installation wizard, desktop shortcut, Start menu entry, and all documentation
- No Python or technical knowledge required for installation
- Portable version option for USB/network deployment

WORKFLOW EXAMPLE
================================================================================

Original .org file:
-------------------
MAILINGLIST
NOTSENDER
alexminglai@gmail.com
bob@hotmail.com
carol@yahoo.com
ann.hsieh@cbcmgroups.org

After Phase 3 cleanup (assuming carol@yahoo.com had migration error):
----------------------------------------------------------------------
MAILINGLIST
NOTSENDER
badminton.ms365@cbcmgroups.org
!ALIAS alexminglai@gmail.com
!ALIAS bob@hotmail.com
carol@yahoo.com
ann.hsieh@cbcmgroups.org

Explanation:
- badminton.ms365@cbcmgroups.org - ADDED as ACTIVE member (routes emails to MS365)
- alexminglai@gmail.com - MODIFIED: prefixed with !ALIAS (successfully migrated to MS365)
- bob@hotmail.com - MODIFIED: prefixed with !ALIAS (successfully migrated to MS365)
- carol@yahoo.com - UNCHANGED: migration had ERROR, remains active (can retry later)
- ann.hsieh@cbcmgroups.org - UNCHANGED: not a target domain, remains active

Email Delivery Flow:
--------------------
When email is sent to badminton@cbcmgroups.org:
1. Mailkeeper processes the distribution list
2. Delivers to:
   - badminton.ms365@cbcmgroups.org → MS365 distribution group → forwards to:
     - alexminglai@gmail.com
     - bob@hotmail.com
   - carol@yahoo.com (direct delivery, still in Mailkeeper)
   - ann.hsieh@cbcmgroups.org (direct delivery, internal user)
3. All recipients receive the email successfully

FURTHER CONSIDERATIONS
================================================================================

1. Incremental migration tracking: 
   Should the tool track which domains have been fully migrated to prevent 
   duplicate operations? 
   Recommendation: Add migration history log (JSON) to track completed domains and dates

2. MS365 group type: 
   Should these be Distribution Lists or Microsoft 365 Groups (with Teams integration)? 
   Recommendation: Use Distribution Lists (mail-enabled security groups) for 
   simplicity unless collaboration features needed

3. Email validation level: 
   Should the tool validate that emails still exist/are active before migration? 
   Recommendation: Optional validation via MS Graph API (check if external user, 
   skip validation for now to keep scope manageable)

4. Multi-platform support:
   Should the tool support macOS and Linux installations?
   Recommendation: Start with Windows (primary user base), consider cross-platform 
   packaging (PyInstaller supports all platforms) in future versions

5. Enterprise deployment:
   Should we create MSI installer for Group Policy deployment?
   Recommendation: Start with Inno Setup EXE, create MSI if enterprise deployment 
   is required
